Porting RobotJS to Rust: tests first, then benchmarks

Rusty Robot lets a Rust program move the mouse, type, take screenshots, and find pixels or images. We rebuilt RobotJS’s implementation in Rust, starting with its tests. Here is what changed—and how the two compare.

Priyankar Kumar · October 29, 2026 · Built with coding agents; verified with automated tests and live desktop checks.

What is it for? Add desktop control to an app, an automated test, or an AI agent. For example: capture a screen, find a known button image, move the pointer to it, and click. Your program decides what to do; the library supplies input, capture, and image operations.

What did we build? A new Rust implementation of RobotJS’s tested behavior. The searches, bitmap handling, BMP codec, and platform integration are Rust code. PNG uses a Rust crate. It does not link or ship RobotJS’s C/C++ addon.

First, check that it does the right thing

A correctness test asks “did this return the expected answer?” A benchmark asks “how long did it take?” We used both. The videos show desktop tasks; the graphs compare individual API timings; these examples explain the checks behind the implementation.

We cloned RobotJS separately, pinned its revision, and mapped its tests before filling in the Rust implementation. That gave the port a concrete target: preserve the behavior exercised by the upstream suite, while expressing it through a Rust API.

The mapping covers 77 expanded upstream cases. Six become compile-time contracts because Rust integer fields cannot represent inputs such as NaN or fractional dimensions. The other 71 have runtime tests. Argument-count and type checks contribute 31 compile-fail examples in total. Those counts describe the recorded contract; they do not establish complete RobotJS parity on every platform. The mapping and API decisions are checked in.

We separated bitmap validation and search, image codecs, keyboard/mouse sequencing, and native platform backends. That let most tests run without touching the desktop. JavaScript exceptions became Rust errors; a missing match became None, an empty vector, or zero. Signed desktop coordinates preserve displays positioned to the left of the main monitor.

Tests then expanded around cases the original suite did not exhaust: overlapping image matches, row padding, malformed files, coordinate rounding, and keyboard cleanup after injected failures. Small exhaustive image patterns helped check that first-match, all-match, and count operations agreed.

Image search: do overlaps and image edges work?

Search every binary 3 × 3 image and valid color-search rectangle, plus small template patterns. Check that the first match, full list, and count agree, including overlapping matches and edges. See the tests.

File roundtrips: do the same pixels come back?

Save generated images, load them again, and compare their pixels. Vary row padding, channel layouts, and orientation. Separate malformed-file cases check that invalid headers and truncated images return errors. See the tests.

Keyboard and mouse: did the app receive the input?

Send input to a disposable test window and observe the resulting text, clicks, and pointer position. Stop if focus leaves that window. A successful API return alone is not enough. See the tests.

Capture: is this a fresh image with the right pixels?

Change a visible patch, capture it, and check the returned color and dimensions. Separate checks cover checkerboards, corners, tiny regions, and cursor exclusion. See the recorded checks.

Measure the API a Node developer actually uses

RobotJS already does its heavy work in a native C/C++ addon. The comparison is Rust’s API versus RobotJS’s JavaScript API and native addon, not Rust versus screen capture written in JavaScript. We wanted to measure the cost of completing the same operation through each public API, including its wrappers and returned values.

The October 27 experiment covered 21 operations: reading pixels already in memory, finding and counting colors, matching image templates, loading and saving images, querying the desktop, and taking screenshots. We ran RobotJS 0.9.1 at a pinned commit on Node 24.22.0, built with node-gyp Release and PNG enabled. Rust used its normal Cargo release profile. Both ran on the same Apple M6 Mac with 32 GiB RAM and macOS 27.0.

  1. Give both implementations the same fixtures. A generated 1920 × 1080 image contained a known 32 × 32 template. Separate cases placed a match early, late, or nowhere. Dense fixtures tested returning thousands of results.
  2. Check answers before timing. The runners asserted search positions, counts, dimensions, and known decoded pixels, then compared compatible observations across languages. Rust consumed results through black_box.
  3. Warm up and repeat. Each operation ran in a fresh process per round, with five warmup calls and seven adaptive timing batches. We ran three rounds sequentially, shuffled case order, and reversed Rust/Node order in the middle round.
  4. Keep the raw results. Reported times are medians of 21 batch averages. They are not individual-call tail latencies. Builds and fixture generation were outside the timer; file I/O used warmed caches and did not force writes to durable storage.

Those choices still leave differences worth knowing. Returning a Rust vector and returning an array of JavaScript objects have different costs. The image APIs also use different decoded and saved formats. These are measurements of the APIs people call, with those differences recorded in the method and original baseline. The orchestrator, Node runner, and Rust runner are checked in.

The first port was not automatically faster

The first measurements showed Rust taking about 1.6× as long to count an absent color and about 3× as long to load a BMP. A rewrite had preserved behavior, but it had also introduced avoidable work. We inspected RobotJS’s implementation and applied the same basic approaches to the Rust port.

Exact colors do not need distance arithmetic. Following RobotJS’s rgb.h, exact searches compare packed RGB values and ignore alpha. Rust walks validated row slices in fixed-size pixel chunks. Approximate matches still use the existing squared-distance calculation. The paired run brought an absent-color search from 1,477 µs to 516 µs.

Image search can reject a candidate sooner. Following bitmap_find.c, we compared the template’s pixels backwards and skipped distance arithmetic for exact matches. Candidate positions still advance in row-major order, preserving the first result and overlapping matches. The tested exact searches ran about 1.13× faster than the previous Rust build, but the direction is data-dependent: tolerant search measured about 2.7% slower.

BMP I/O should operate on rows and buffers. Compatible BGRA rows can be copied directly; BGR rows can be expanded in chunks. For saving, we followed bmp_io.c and assembled one payload for a bulk write instead of calling the buffered writer per pixel. Saving traded an extra output-sized allocation—6.22 MB in this fixture—for fewer writer calls. Allocation is fallible and happens before opening the output file.

Regression coverage grew with the changes: arbitrary alpha and row padding, distinct RGB channel permutations, overlapping matches, tolerance boundaries, and byte-identical BMP output across all four row alignments. The exhaustive suites covered binary 3 × 3 images, binary 2 × 2 templates, and 1,904 codec roundtrips. The bitmap-only change passed 113 headless tests with PNG and 103 without; those configurations overlap and include compile-fail contracts.

How the optimized port compared with RobotJS

In the October 27 Node comparison, Rust had lower medians in 17 of 21 operations. That count includes near-ties with overlapping round ranges. It is not an overall application speedup, and this experiment did not measure typing, click delivery, or complete automation workflows.

Open the benchmark results.

The 267.50× result needs context. That fixture returns 65,536 matches. Rust returns a Vec<Point>; RobotJS constructs JavaScript objects. It measures search plus result creation across different APIs. It does not mean the scan itself got 267× faster. The late and absent color searches, at about 2×, are more useful when thinking about scanning a large image for one match.

The losses stayed in the report. BMP loading still took Rust about 13% longer while producing BGRA32 instead of RobotJS’s smaller BGR24 buffer. Display enumeration took about 27% longer. Single-pixel and small-region capture were substantially slower. Exact image search and full-screen capture had overlapping round ranges, so their small median advantages are not convincing wins.

A successful API call is only part of the test

A keyboard API can return successfully while text goes to the wrong window. A screenshot can have the right dimensions while containing an old frame. Unit tests alone cannot catch either mistake.

We used disposable Chromium and native AppKit fixtures to observe text, clicks, and pointer positions. Input runs stop when the owned window loses focus. Headless runs report ignored desktop cases separately; they do not count those cases as passes. Linux/X11 and Windows also have native desktop CI, with their omissions recorded.

The test harness needed fixes too. On hosted Linux, Chromium’s GPU initialization prevented the fixture from becoming ready under Xvfb. We disabled GPU rendering for that fixture in hosted CI and kept the input assertions. It was a reminder to distinguish “the app never opened” from “the automation sent the wrong event.”

For capture, the fixture changes a patch between red and green before each timed call. The runner waits for presentation outside the timer, then checks the returned patch and dimensions. A separate 115-capture check exercises palette colors, a fine checkerboard, tiny rectangles, display corners, and cursor exclusion. The quality evidence records what was checked.

The Node comparison exposed the next bottleneck

The first macOS implementation captured the containing display and cropped it afterward. That helped avoid partially transparent tiny captures, but asking for one pixel still incurred full-display capture work.

Version 0.1.3 uses ScreenCaptureKit’s direct rectangle capture API on macOS 15.2 and newer. It retains the earlier path on macOS 14. A shared, thread-safe Core Image context handles rendering to an owned sRGB buffer. Reusing that context preserves rendering state across calls; every call still captures new pixels.

  1. Capture the requested rectangle.
  2. Render the tagged image into sRGB, sampling pixel centers when reducing to logical size.
  3. Wait for rendering to complete before returning the owned CPU buffer.

That last step matters at the native boundary. Returning before rendering finishes would make a short timing meaningless and could expose a buffer that is still being written. The implementation propagates render errors, and regression tests cover orientation, exact sampling, alpha, invalid dimensions, and concurrent use.

In a separate October 28 experiment, the new path reduced repeated full-display capture from 50.98 ms to 22.31 ms and 100 × 100 capture from 44.20 ms to 9.57 ms against the previous Rust binary. The capture report records the runs, freshness checks, and a comparison with another Rust capture library.

That is a Rust before/after result. We have not rerun the latest capture implementation against RobotJS. Combining the old Node times with this later run would not establish a current Node speedup. The October 27 table above deliberately retains the capture losses that prompted the work.

Test the package people will install

Build success was followed by package checks. The release workflow builds and installs Node archives for seven OS/architecture targets, including minimum and current supported Node versions. Only the core crate is published to crates.io; the media and Node bridge crates remain workspace components.

For 0.1.3, a fresh consumer downloaded the crate from the registry instead of using a local path dependency. The local run passed 65 public API tests with PNG and 55 without; desktop tests were explicitly excluded from that headless run. Registry-consumer CI passed on Linux, macOS, and Windows. The downloaded GitHub crate archive matched the crates.io checksum byte for byte.

Coding agents did much of the implementation and iteration. The useful discipline was to make each claim inspectable: a test mapping for compatibility, observed app state for input, raw samples for latency, and a registry install for publication. Those checks exposed mistakes in the implementation, the fixtures, and the initial assumptions about performance.

There is more to do: native Wayland support, broader keyboard layouts and physical display configurations, and equivalent performance measurements on other machines. The source and harnesses are public so those gaps can be tested and narrowed.
