Building Rusty Robot · An engineering story

Rebuilding RobotJS in Rust, one test at a time

I wanted a desktop automation library for the tools and agents we are building. Codex and I started with RobotJS’s tests, rebuilt the implementation in Rust, and then had to earn the speedups.

By Priyankar Kumar, built with Codex · October 30, 2026 · Core crate 0.1.3

The starting request was straightforward: clone RobotJS and port its tests to Rust first. RobotJS gives a Node.js program the basic tools to use a desktop: move the mouse, press keys, take screenshots, and search those images. I wanted those capabilities in an independent Rust library that an app, a test runner, or an AI agent could compose.

That became Rusty Robot. It now has a published MIT-licensed Rust crate, native input and capture backends, image search, regression tests, and recorded comparisons against RobotJS. Some image tasks became much faster. Other operations stayed close, and some remained slower.

In this story, “we” means me and Codex. I set the direction, tested the product, and kept pushing on the results: benchmark against Node, show useful examples, check that the comparisons are fair. Codex implemented, ran tests, investigated failures, and built the reports. The back-and-forth changed both the code and what we could honestly say about it.

01 · The foundation

First, define what the rewrite must preserve

“first port all the tests to rust”

My starting instruction to Codex

There was an important detail in the code we cloned: RobotJS already runs its heavy work in C and C++. JavaScript exposes the API; a native addon does the scanning, capture, and input. Rebuilding it in Rust meant replacing an existing native implementation and its JavaScript boundary.

RobotJS

  1. Your Node.js program
  2. RobotJS JavaScript API
  3. RobotJS C/C++ addon
  4. Operating system

Rusty Robot

  1. Your Rust program
  2. Rusty Robot Rust API
  3. Rust implementation
  4. Operating system

Rust calls Apple frameworks, Windows APIs, or Linux/X11 for capture and input.

Our image searches, bitmap handling, BMP codec, and platform integration are Rust code; PNG uses a Rust crate. Rust still calls the operating system’s native APIs. The core library does not ship RobotJS’s C/C++ addon or require Node. A separate Node bridge lets JavaScript applications call the new implementation.

What was the actual scope of the rewrite?

The pinned RobotJS revision has 9,718 physical lines under src/, plus 265 in index.js and index.d.ts. That count includes comments, blank lines, and bundled headers. The source we started from is roughly ten thousand lines. Dependencies and generated build output are excluded.

We used RobotJS commit 0af6073e1f1bcff865ffe52801c71647829cdc1c. The file-by-file count records exactly what was counted. The goal was to preserve the tested behavior through a Rust API; it was not a claim of exhaustive compatibility with every upstream behavior.

We mapped 77 expanded upstream test cases before filling in the implementation. Seventy-one became runtime checks. Six became compile-time contracts because inputs such as fractional dimensions cannot be represented by the Rust API’s integer fields. Across argument and type rules, the suite has 31 compile-fail examples: programs that must refuse to compile.

We divided the work into bitmap search, image codecs, keyboard and mouse sequencing, and native platform backends. This let most tests run without touching a desktop. A missing match became None, an empty vector, or zero; errors became Rust results. Signed desktop coordinates kept monitors to the left of the main display representable.

Then we expanded the tests. A port that handles the examples can still get row padding, overlapping matches, or a held modifier wrong. We checked small images exhaustively, round-tripped generated files, and watched disposable applications receive real input.

Image search: do overlaps and image edges work?

Search every binary 3 × 3 image and valid color-search rectangle, plus small template patterns. Check that the first match, full list, and count agree, including overlapping matches and edges. See the tests.

File roundtrips: do the same pixels come back?

Save generated images, load them again, and compare their pixels. Vary row padding, channel layouts, and orientation. Separate malformed-file cases check that invalid headers and truncated images return errors. See the tests.

Keyboard and mouse: did the app receive the input?

Send input to a disposable test window and observe the resulting text, clicks, and pointer position. Stop if focus leaves that window. A successful API return alone is not enough. See the tests.

Capture: is this a fresh image with the right pixels?

Change a visible patch, capture it, and check the returned color and dimensions. Separate checks cover checkerboards, corners, tiny regions, and cursor exclusion. See the recorded checks.

One native test caught a particularly tangible bug: hold both Shift keys, release one, and type. Our implementation produced aa where the app should receive Aa. We fixed modifier tracking per physical key and added regressions for both release orders. That is the kind of behavior a successful build cannot establish. The validation record keeps the failures, fixes, and tested scope.

02 · A working port meets the stopwatch

The first Rust version was not automatically faster

Once the tests passed, I asked for a comparison against RobotJS. The first measurements were a useful correction to our expectations: Rust took about 1.6 times as long to count an absent color and about three times as long to load a BMP. We had moved the behavior to Rust and brought avoidable work along with it.

“if rust implementation can be made faster on some of these purely by following the same algos as robotjs, lets do it”

My next instruction after the first comparison

RobotJS became our optimization reference as well as our compatibility reference. Three changes mattered:

  1. Compare exact colors directly. An exact match does not need color-distance arithmetic. Following RobotJS, we compared packed RGB values, ignored alpha, and walked validated rows in fixed-size pixel chunks. Approximate matches kept their distance calculation.
  2. Reject image candidates sooner. We followed RobotJS’s backwards comparison of a candidate’s template pixels while preserving the order of candidate positions. Exact searches improved, but tolerant search became about 2.7% slower in the paired run. The effect depends on image content.
  3. Move image data in bulk. BMP loading copies compatible rows or expands them in chunks. Saving assembles a payload and writes it once, instead of making a writer call per pixel. It uses an extra output-sized buffer—6.22 MB for this fixture—to reduce call overhead.

We kept the old executable and measured it alongside the new one, reversing execution order in the middle round. The changes also gained regression coverage for channel order, alpha, padding, overlaps, and byte-identical BMP output. The suite included 1,904 codec roundtrips. The improvement came from doing less work while preserving the answer.

Then we compared the optimized port with Node again

Rust had lower medians in 17 of 21 API operations. That included near-ties with overlapping ranges. Scanning for a late or absent color was about twice as fast; exact image search was approximately tied. BMP loading still took about 13% longer, producing a larger pixel buffer, and small screenshots were substantially slower.

The largest number was 267.50× for returning 65,536 color matches. That included constructing JavaScript objects versus a Rust vector. It was a real API cost, but it did not mean the pixel scan itself was 267 times faster. I wanted examples that made the differences easier to understand.

Explore the 21 API results and how we measured them

This October 27 experiment compares each public API, including wrappers and result allocation. Both implementations used the same fixtures on one Apple M6 Mac with 32 GiB RAM and macOS 27.0. RobotJS 0.9.1 at the pinned revision used Node 24.22.0 and a Release C/C++ addon with PNG enabled; Rust used a Cargo release build.

There were three sequential rounds, with case order shuffled and library order reversed in the middle round. Each fresh process warmed up five times, then ran seven adaptive batches. Reported medians summarize 21 batch averages; they are not individual-call tail latencies. Expected outputs were checked. File I/O used warm caches without forcing durable writes; decoded and saved formats differed where documented.

03 · Put the gains to work

What faster image analysis buys an automation

We tested three tasks on generated screenshots with known colors and layouts: collect Ready badges, find a failed deployment, and count passing test tiles. Both libraries received identical pixels already loaded into memory; capture and image loading are excluded.

Each time is the median of six 60-image batches, with every answer checked. A 2× speedup means half the analysis time. These are comparisons of the public APIs on one Mac.

Shared method, machine, and limits

Both receive identical preloaded 1920 × 1080 BGRA32 buffers. Each fresh process completes and verifies a full warmup. Six rounds alternate library order. No recording runs during measurement; outputs are checked after the timer. There are no artificial sleeps in the timed analysis.

Apple M6, macOS 27.0, Node 24.22.0, Rust 1.99.1 release builds; RobotJS commit 0af6073. Allocation and public API wrapper costs are included. Capture, PNG decoding, disk reads, and warmup are excluded.

04 · Input delivery

Typing did not show the same gains

We filled the same 24 form fields through native keyboard input and checked every saved value. RobotJS was faster at zero requested keyboard delay; at a matched typing rate, the two were effectively tied.

Both libraries entered the same records through native input into an owned Chrome form. Mouse delay was 10 ms and key-tap delay was zero for both. One warmup per backend and profile preceded six alternating measured trials, without recording. Every saved field matched in every trial.

The earlier default-delay demo favored Rust because RobotJS waited per character while Rust batched text. Its typing pace was not matched; the table above uses explicit timing profiles.

Rust retains a 10 ms minimum interval between native Unicode text batches to preserve delivery. Reducing that delay remains a performance opportunity, provided applications still receive every character correctly.

05 · The cost before image search even begins

A faster scan cannot rescue a slow screenshot

The image-analysis wins start with pixels already in memory. A desktop agent needs to obtain those pixels first. The Node comparison made that bottleneck obvious: a small capture took the early Rust backend about 25.95 ms versus RobotJS’s 4.78 ms.

Our first macOS path captured the containing display and cropped afterward. That had helped avoid partially transparent tiny captures, but a request for one pixel still paid for a whole display. Version 0.1.3 uses ScreenCaptureKit’s direct rectangle capture on macOS 15.2 and newer, with the earlier path retained for macOS 14.

We also reused a thread-safe Core Image rendering context. Each call still captures a fresh image, renders it into an owned sRGB buffer, and waits for rendering to finish before returning. Reusing the rendering machinery saves setup work; reusing an old frame would change the behavior.

To check freshness, we changed a visible patch between red and green before each timed capture and verified the returned pixels. A separate 115-capture check covered palette colors, a fine checkerboard, tiny regions, display corners, and cursor exclusion. Color, scale, and orientation matter as much as latency when the next step is to click a detected target.

Inspect the capture implementation and quality evidence

The path samples pixel centers when reducing to logical size, propagates rendering errors, and returns only after the CPU buffer is ready. Regressions cover orientation, sampling, alpha, invalid dimensions, and concurrent use. Capture results and method · Recorded quality checks.

The open performance question is the complete loop: capture a fresh screen, find a target, send input, and observe the application change. We have not rerun the latest capture backend against RobotJS. A current capture comparison and a full-loop benchmark are needed before claiming that an entire automation is faster.

06 · From a port to a library people can use

Ship the package, keep the unfinished work visible

We published the core as rusty-robot-desktop, imported in Rust as rusty_robot, under MIT with RobotJS attribution retained. It supports macOS 14+, Windows, and Linux/X11. Native Wayland support remains unfinished.

Shipping meant checking what a user would install. A fresh consumer downloaded 0.1.3 from the registry instead of using our local source tree. That run passed 65 public API tests with PNG and 55 without; desktop tests were excluded from those headless counts. Registry-consumer CI passed on Linux, macOS, and Windows. We also added an agent integration skill with API recipes and verification guidance.

What do the release and platform checks actually cover?

The normal CI checks formatting, linting, contracts, documentation, and benchmark evidence. Native desktop validation has separate Windows and Linux/X11 runs, and macOS has local observed-input and capture checks. Ignored desktop tests are reported separately from passes. These checks do not cover every physical display configuration or application.

The Node release workflow builds and installs archives for seven OS/architecture targets and checks supported Node versions. The core crate is on crates.io; media and Node bridge crates are separate workspace components. The article’s Rust-versus-RobotJS timings use the Rust API, not that Node bridge.

What we still need to get right

The remaining work has concrete acceptance criteria. Version 0.1.3 is an early release, and these are the gaps that matter to someone building on it:

Complete automation latency
Measure the latest capture-to-action loop against RobotJS, including a visible response from the target app. Keep scan-only improvements separate until then.
Reliable input across more setups
Extend observed text and modifier tests to more keyboard layouts, applications, and OS versions. Any reduction in typing delays has to preserve delivery.
Capture across real displays
Expand physical multi-monitor, mixed-scale, permission-change, and hot-plug checks. A fast buffer with stale pixels or the wrong coordinates is a failed capture.
Performance beyond this Mac
Repeat matched comparisons on Windows, Linux, and other hardware. Broaden the image corpus beyond these known-color generated layouts; small exact-image-search differences need stronger evidence.
Native Wayland
Add and validate a backend for that environment. The current Linux support is X11; passing X11 tests does not establish Wayland support.

Working with Codex made it practical to keep implementing, testing, and revisiting the design. It also made review of the evidence essential: the first port was slower in places, and an input bug survived until an app received the events. Each of those changed what we built next.

We now have an independent Rust library with measurable image-analysis gains and a clearer view of the hard parts. The next step is to carry those gains through the whole desktop interaction, with the same standard we started with: check what actually happened.
